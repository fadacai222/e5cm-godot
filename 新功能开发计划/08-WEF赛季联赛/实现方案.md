# WEF 赛季联赛实现方案

## 1. 功能定位

项目已经保留 WEF 大模式按钮、标题素材和排行榜音乐。WEF 应成为正式竞技入口，但不能一上来就做“客户端直接上传分数”的假排行榜。正确路线是：

1. 本地离线赛季验证规则是否好玩。
2. 导出可验证成绩包。
3. 只读在线排行榜试验。
4. 服务端验证和账号体系成熟后开放提交。

实时联网对战不在本方案范围内。

## 2. 赛季结构

### 本地赛季 MVP

- 每个赛季持续 2～4 周。
- 固定 5～8 首赛季曲目。
- 每首可无限练习，但正式提交次数有限，例如 3 次。
- 赛季总分按最佳有效提交计算。
- 额外统计稳定性、总 Miss、最高 Combo 和完成曲数。
- 本机多个独立玩家档案可生成本地排名。

### 分组

首版不按复杂 Elo，建议按玩家最高模式等级或资格赛结果分组：

- 新秀组。
- 进阶组。
- 精英组。

分组只影响曲目难度和展示，不影响判定窗口。

## 3. 赛季规则

每个 SeasonManifest 必须完整固定：

```gdscript
{
  "season_id": "WEF-2026-S1",
  "schema_version": 1,
  "title": "霓虹启航赛季",
  "starts_at": 0,
  "ends_at": 0,
  "judge_version": 1,
  "parser_version": 1,
  "ruleset_id": "wef_standard_v1",
  "charts": [
    {"chart_hash": "...", "attempt_limit": 3, "weight": 1.0}
  ],
  "scoring": {
    "type": "weighted_best_score",
    "tie_breakers": ["accuracy", "miss", "max_combo", "submitted_at"]
  },
  "reward_ids": []
}
```

赛季开始后不能静默修改曲目或规则。若必须修订，增加 manifest revision 并明确作废规则。

## 4. 正式提交流程

1. 玩家选择赛季曲目。
2. 进入“练习”或“正式尝试”。
3. 正式尝试开始前扣除一次本地尝试 token，并保存 pending 状态。
4. 完成后通过 RunEligibility。
5. 写入成绩、鬼影/回放摘要和完整验证字段。
6. 结算成功后把 pending 标为 completed。
7. 崩溃发生在开局前可返还；已经开始判定后不自动返还，避免强退刷尝试。

尝试次数规则必须在 UI 中非常清楚，且本地时钟异常不能重置次数。

## 5. 评分建议

首版主排名按加权最佳分总和，依次使用以下同分规则：

1. 总准确率。
2. 总 Miss 更少。
3. 总最大 Combo 更高。
4. 更早完成全部有效提交。

不要把游玩次数或付费内容转换成排名优势。

可额外提供不影响主排名的榜单：

- 全连榜。
- 稳定性榜。
- 单曲榜。
- 新秀进步榜。

## 6. 本地数据

建议：

```text

user://seasons/<season_id>/submissions/<submission_id>.e5score
```

Submission：

```gdscript
  "client_build": "0.9.1",
  "created_at": 0,
  "status": "local_valid"
}
```

## 7. 成绩验证等级

### Level 0：客户端声明

只有最终分数，无可信度。仅用于开发调试，不进入正式榜。

### Level 1：结构验证

检查 chart_hash、版本、总判定数、分数范围和 checksum。适合本地赛季。

### Level 2：事件重放验证

上传紧凑判定/输入记录，由服务端重新计算分数、Combo、准确率和资格。

### Level 3：强反作弊

包含签名构建、设备风险、异常行为检测和人工复核。只有公开高价值赛事才值得投入。

WEF 首个在线版本至少需要 Level 2，不能只相信客户端 JSON 中的分数。

## 8. 在线架构建议

### 客户端

- `SeasonService`：赛季 manifest、状态和本地提交。
- `LeagueApiClient`：带超时、重试、离线队列，但不阻塞主线程。
- `SubmissionVerifier`：本地预检。
- `AccountLinkService`：未来账号绑定，和游客档案分离。

### 服务端最小能力

- 发布签名 SeasonManifest。
- 账号与玩家 ID。
- 接收成绩包。
- 异步重放验证。
- 排行榜查询。
- 赛季冻结和结算。
- 作废异常提交。
- 审计日志与限流。

客户端不得拥有排行榜写数据库的直接凭证。

## 9. Manifest 安全

在线 manifest 必须有数字签名或至少通过 TLS + 服务端签名校验。客户端只信任内置公钥签名的赛季配置。

必须限制：

- 曲目数量。
- 字段长度。
- 奖励 ID 必须来自本地 RewardCatalog。
- URL 域名白名单。
- 时间范围和版本兼容。

验证失败时保留上一个有效赛季或切换离线赛季，不阻止游戏启动。

## 10. 离线行为

- 已下载赛季可以离线游玩和本地记录。
- 在线提交进入待上传队列。
- 排行榜显示最后同步时间。
- 赛季截止后离线产生的成绩是否接受，由服务端规则决定；客户端不能保证。
- 网络失败不得卡在加载页面，必须可返回普通模式。

## 11. UI

### WEF 首页

- 当前赛季名称和剩余时间。
- 分组与本地/在线排名。
- 曲目完成度和剩余正式尝试。
- 赛季规则、奖励和同步状态。

### 正式尝试确认

必须二次确认：

```text
本次将消耗 1 次正式尝试
剩余：2 / 3
异常退出可能不会返还
```

### 排行榜

- 本地榜和在线榜明确分栏。
- 在线数据有最后更新时间。
- 未验证成绩显示“审核中”，不混入正式排名。

## 13. 分期实施

### WEF-0：规则原型

- 本地固定赛季。
- 本机玩家排名。
- 有限正式尝试。
- 收藏奖励。

### WEF-1：成绩包

- 导出 `.e5score`。
- 离线重放验证工具。
- 手工汇总赛事测试。

### WEF-2：只读在线

- 下载签名 manifest。
- 查看在线排行榜。
- 客户端仍不提交成绩。

### WEF-3：受控提交

- 小范围账号测试。
- 服务端重放验证。
- 待审核、通过、作废状态。

### WEF-4：正式赛季

- 赛季冻结、奖励发放、申诉和运营工具。

## 14. 不做事项

- 不做实时联网对战。
- 不让客户端直接决定最终排名。
- 不把本地系统时间作为在线截止真值。
- 不把自动播放、训练或非标准修饰器成绩提交。
- 不在没有服务端验证时开放公开排行榜写入。

## 15. 验收标准

- 本地赛季可完整开始、提交、排名和结算。
- 尝试次数在崩溃和重复结算下保持幂等。
- manifest 修改后能识别 revision，不混算成绩。
- 自动播放、训练、派对和非标准爬塔成绩全部拒绝。
- 同分规则稳定可重算。
- 网络失败、签名失败和服务端超时不影响普通游戏。
- 排行榜明确区分本地、待验证和正式成绩。

## 16. 风险与回滚

| 风险 | 处理 |
|---|---|
| 客户端分数可篡改 | 在线至少使用事件重放验证 |
| 赛季规则中途改变 | manifest revision 和赛季冻结 |
| 强退刷尝试次数 | pending token 和开始判定后的不可返还规则 |
| 网络拖慢主流程 | 全异步、超时、离线缓存和返回入口 |
| 服务端成本失控 | 先本地规则验证，再小范围上线 |
| 账号绑定丢档 | 本地档案与在线身份分离并提供显式绑定 |

回滚时重新锁定 WEF 入口或只保留本地赛季；普通模式、玩家档案和曲库不依赖在线服务。
